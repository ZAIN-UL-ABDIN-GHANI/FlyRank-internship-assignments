# FL-07: AI Architecture & Code Review Copilot — Hardening & Extension

## 1. FL-06 Summary

FL-06 delivered a working LangGraph agent, exposed via FastAPI, with three chained capabilities:

- **Foundation** — FastAPI skeleton + a single `gather_requirements` LangGraph node that asks one
  clarifying question at a time until a feature request is fully specified.
- **RAG/FAISS** — a `kb/` folder (development rules + LangGraph/FastAPI/RAG best practices), chunked,
  embedded (sentence-transformers), indexed in FAISS, retrieved via a `retrieve_context` node and injected
  into every downstream prompt.
- **Planning agent** — `generate_plan` node producing a structured `ImplementationPlan` (tech stack + small
  sequential phases) via schema-enforced structured output, gated behind `requirements_complete`.
- **Code review agent** — `review_code` node producing a structured `CodeReviewReport` (severity-ranked
  findings: security/performance/SOLID/duplication/bugs), gated behind a supplied `code` string, with its
  own code-specific FAISS retrieval merged into the planning-stage context.
- **Finalization** — logging, startup config validation, a global exception handler, pinned dependencies,
  README, and a rolling `project_summary.md`.
- **Provider swap** — `ChatAnthropic` replaced with `ChatGoogleGenerativeAI` (Gemini via Google AI Studio,
  official `google-genai` SDK under `langchain-google-genai`); zero changes to nodes, prompts, schemas, or
  tests (all LLM calls are mocked at the `_build_llm`/`_build_planning_llm`/`_build_review_llm` boundary).

**Status:** 23/23 tests passing, full pipeline verified end-to-end via the real HTTP layer with LLM calls
mocked at the `_build_llm`/`_build_planning_llm`/`_build_review_llm` boundary (no live Gemini call has been
made in this sandbox - see Section 8).

**Known limitations carried into FL-07:** no server-side session store (client resends full history every
call); `code` is a single string (no multi-file or native Git diff parsing); no standalone "just review
this" path (review is gated behind completed requirements-gathering + a generated plan).

## 2. Project Overview

A LangGraph-orchestrated copilot that gates feature work behind clarified requirements, grounds its plan
and review output in a retrieved, versioned set of project rules, and returns schema-validated results over
a small FastAPI surface. FL-07 hardens this into something usable day-to-day and closes the gaps above.

## 3. Problem Statement

Solo development drifts without a forcing function: features get scoped loosely, plans skip established
conventions, and code review is inconsistent or skipped under time pressure. FL-06 built the automated
gate; FL-07 makes it practical to use repeatedly (sessions instead of resending history), on more realistic
inputs (diffs, multiple files), and in more contexts (review without a full planning cycle), then packages
it for actual deployment rather than local-only use.

## 4. Goal

Extend the FL-06 copilot with persistent sessions, richer code-review input, a standalone review path, and
deployment packaging — without altering the existing requirements → retrieval → plan → review pipeline.

## 5. Scope

**In scope:**
- Server-side session persistence (SQLite) keyed by `session_id`.
- Git unified-diff parsing and multi-file review input.
- A standalone `/agent/review` endpoint that skips requirements-gathering/planning entirely.
- Dockerfile + GitHub Actions CI running the test suite on push.

**Out of scope (explicitly deferred):**
- Multi-user auth/authorization.
- A frontend/UI.
- Managed cloud deployment automation (Docker image is the deliverable; hosting is the user's choice).
- Full observability/APM (structured logging from FL-06 remains the extent of this).

## 6. Build Platform & Justification

Continuing on the FL-06 platform: scripted Python (FastAPI + LangGraph + LangChain + FAISS, Gemini-backed).
**Alternative considered:** rebuilding on a managed workflow tool (e.g. n8n) for faster session/deployment
features out of the box. Rejected — it would discard the verified graph, schemas, and 23 passing tests for
marginal convenience gains, and the remaining FL-07 work (SQLite, diff parsing, Docker) is standard Python,
not a reason to change platforms.

## 7. Tech Stack

Existing: Python 3.12, FastAPI, LangGraph, LangChain core, `langchain-google-genai` (Gemini), Pydantic,
sentence-transformers, FAISS, pytest.
New in FL-07: `sqlite3` (stdlib — session store), `unidiff` (parsing Git unified diffs), Docker, GitHub
Actions.

## 8. Live Tool/Data Connection

- **Google AI Studio (Gemini)** — the integration is real: `ChatGoogleGenerativeAI` genuinely attempts a
  network call to `generativelanguage.googleapis.com` with the configured model name on every LLM node.
  Confirmed directly (unmocked) in this sandbox: the call reaches that host and fails only with a 403
  "host not in allowlist" from the sandbox's own network egress policy - not an application error - and the
  app degrades correctly (clean 502 with a descriptive message, not a crash). **A successful live call with
  a real `GOOGLE_API_KEY` has not been made in this sandbox** (it has no route to that host); this should be
  confirmed once in a normal environment before/during the final screen recording.
- **Local FAISS index** — built from `kb/*.md`; genuinely indexed and queried in tests (real chunking, real
  FAISS search); only the embedding *vectors* are a local fake stand-in in this sandbox (no route to
  `huggingface.co` either) - the real `sentence-transformers` model is used automatically wherever network
  access exists.
- **New: local SQLite file** (`data/sessions.db`) — session history; no external connection; fully verified
  with real file I/O.
- No new third-party live connectors are introduced in FL-07.

## 9. System Architecture

```
Client --session_id + message--> [Session Store: SQLite]
                                        |
                                   (reconstructed history)
                                        v
                      retrieve_context -> gather_requirements --[incomplete]--> END (question, stored)
                                                               --[READY]--> generate_plan --[no code]--> END
                                                                                           --[code]--> review_code -> END

Client --files/diff (no session)--> /agent/review -> review_code (standalone) -> END
```

The session store wraps graph invocation (load → invoke → persist); `/agent/review` bypasses
`gather_requirements`/`generate_plan` and calls `review_code` directly on parsed diff/file input.

### Sprint 1: Server-Side Session Persistence

**Objective**
Replace client-held full history with a SQLite-backed session store keyed by `session_id`, so clients send
only the new message each call instead of the whole transcript.

**Files to Create/Modify**
- New: `app/session_store.py` — `append(session_id, role, content)`, `get_history(session_id)`, `reset(session_id)`
- New: `tests/test_session_store.py`
- Modify: `app/config.py` — add `session_db_path` (`SESSION_DB_PATH`, default `data/sessions.db`)
- Modify: `app/schemas.py` — `AgentRequest` becomes `session_id: str`, `message: str`, `code: Optional[str]`
- Modify: `app/main.py` — `/agent/gather` loads history by `session_id`, appends the new message, invokes
  the graph, persists the assistant's reply back to the store; add `POST /session/{session_id}/reset`
- Modify: `.env.example`, `.gitignore` (add `data/sessions.db`)

**Implementation Tasks**
1. `session_db_path` setting in `config.py`.
2. `session_store.py`: single table `messages(session_id, role, content, created_at)`, stdlib `sqlite3`, no ORM.
3. Update `AgentRequest`/`AgentResponse` for the new single-message contract.
4. Update `/agent/gather` to read/write through the store; new `/session/{id}/reset` endpoint.
5. Update existing `main.py`-level tests for the new request shape.

**Acceptance Criteria**
- Two sequential calls with the same `session_id` accumulate history server-side; client never resends prior messages.
- A fresh `session_id` starts with empty history.
- `/session/{id}/reset` clears that session's stored messages.
- All FL-06 graph/planning/review behavior is unchanged — existing 23 tests still pass (with only the
  `main.py`-level request-shape tests updated, not the graph/node tests).

**Testing & Verification**
- `test_session_store.py`: append + retrieve roundtrip, ordering, reset.
- Updated `main.py` tests: two-call conversation reaches `requirements_complete: true` only once enough
  info has accumulated across both calls; reset endpoint clears state.
- Full suite re-run after implementation: **31/31 passing** (23 prior + 8 new/updated).

**Build Log (Issue, Fix, Decision)**
- **Issue:** Initial `test_main.py` calls that reached `requirements_complete=True` failed FastAPI response

  **Fix:** patched `app.graph._build_planning_llm` in every test that reaches the READY branch, returning a

  **Decision:** kept `AgentRequest.history` removed entirely (breaking change) rather than supporting both

**Deliverables**

### Sprint 2: Multi-File & Git Diff Support for Code Review

**Objective**
Let `review_code` accept a Git unified diff or an explicit multi-file list, not just one opaque code blob,
so findings can reference the correct file.

**Files to Create/Modify**
- New: `app/diff_parser.py` — `looks_like_unified_diff`, `parse_unified_diff`, `format_files_for_review`
- New: `tests/test_diff_parser.py`
- Modify: `app/schemas.py` — new `CodeFile` model, `AgentRequest.files: Optional[List[CodeFile]]`
- Modify: `app/main.py` — pass `code_files` into graph state, log `files_provided` count
- Modify: `app/graph.py` — `AgentState.code_files`; `review_code` formats `files`/diff/raw input before
  prompting; `_route_after_plan` now checks `code_context` OR `code_files`
- Modify: `tests/test_review_node.py`, `tests/test_main.py` (new coverage, existing states given the new key)
- Modify: `requirements.txt` (`unidiff==1.0.0`), `README.md`

**Implementation Tasks**
1. `diff_parser.py` using the `unidiff` library: detect diff-like input, parse into `{filename, content}`
   per file (content = the hunk text), raise `ValueError` on unparseable diffs (never crash the request).
2. `format_files_for_review`: join files with `=== FILE: <name> ===` boundary markers.
3. `review_code`: priority order is `files` (explicit multi-file) → diff-like `code` (auto-parsed) → raw
   `code` text as-is; on diff parse failure, log a warning and review the raw text instead of failing.
4. Schema/state/routing updates so either `code` or `files` triggers review.

**Acceptance Criteria**
- A Git diff touching multiple files produces per-file `=== FILE: ... ===` sections in the review prompt.
- An explicit `files` list is formatted the same way, independent of `code`.
- A string that merely *looks* like a diff but fails to parse still produces a review (raw-text fallback),
  not a 500.
- Plain single-string `code` (Sprint 1/FL-06 behavior) still works unchanged.
- All prior tests still pass.

**Testing & Verification**
- `test_diff_parser.py` (5 tests): diff detection, multi-file extraction, malformed-diff `ValueError`,
  file-boundary formatting.
- `test_review_node.py` (+4 tests): multi-file formatting, diff parsing, malformed-diff fallback, routing
  when only `files` is given (no `code`).
- `test_main.py` (+1 test): real HTTP call with `files`, asserting both file sections reach the review LLM.
- **Manual end-to-end run** (outside pytest, real `TestClient`, no mocked store): posted an actual Git diff
  through `/agent/gather`; confirmed the logged pipeline (`retrieve_context` → `gather_requirements` →
  `generate_plan` → `review_code: 1 findings`) and inspected the exact prompt sent to the review LLM,
  confirming the diff was parsed into a correct `=== FILE: db.py ===` section with the real hunk text.
- Full suite re-run: **41/41 passing** (31 prior + 10 new).

**Build Log (Issue, Fix, Decision)**
- **Issue 1:** while drafting `tests/test_main.py`, an `str_replace` edit accidentally deleted
  `test_reset_clears_session_history` instead of appending a new test after it.
  **Fix:** caught it by re-viewing the file before running tests; restored the reset test as its own
  function alongside the new multi-file test.
  **Decision:** re-view a file immediately after any edit to it before writing the next edit, rather than
  trusting the diff description alone.
- **Issue 2:** `README.md` still documented Sprint 1's old `history`-list request shape - it was never
  updated when Sprint 1 changed the API contract to `session_id`+`message`, so it had been silently stale
  for one full sprint before this was noticed.
  **Fix:** rewrote the API section with the current `session_id`/`message` contract plus new `files`/diff
  examples.
  **Decision:** treat README/doc updates as part of a sprint's own acceptance criteria going forward, not
  an afterthought caught incidentally in a later sprint - this review formalizes that as a checklist item.
- **Issue 3:** none in the core `diff_parser`/`review_code` logic itself - `unidiff` handled the
  malformed-diff case as expected on the first attempt (raised `UnidiffParseError`, caught and re-raised as
  `ValueError`).
  **Decision:** chose the `unidiff` library over a hand-rolled parser (per the FL-07 plan) specifically
  because it correctly rejects malformed hunks (wrong line counts) rather than silently mis-parsing them.

**Deliverables**
- `app/diff_parser.py`
- Updated `app/schemas.py`, `app/main.py`, `app/graph.py`, `requirements.txt`, `README.md`
- `tests/test_diff_parser.py`; updated `tests/test_review_node.py`, `tests/test_main.py`
- Updated `project_summary.md`

### Sprint 3: Standalone Review-Only Endpoint

**Objective**
Add `POST /agent/review` for code review independent of the session/requirements/planning flow - same
review agent, FAISS retrieval, and schemas, with requirements-gathering and planning fully skipped.

**Files to Create/Modify**
- New: `tests/test_review_endpoint.py`
- Modify: `app/schemas.py` — `ReviewRequest` (`code`, `files`), `ReviewResponse` (`review: dict`)
- Modify: `app/main.py` — new `POST /agent/review` route

**Implementation Tasks**
1. `ReviewRequest`/`ReviewResponse` schemas, reusing the existing `CodeFile` model.
2. Route validates at least one of `code`/`files` is present (400 otherwise, including an empty `files: []`).
3. Route builds a minimal state dict and calls the existing `review_code` function **directly** - no
   `_graph.invoke()`, no `gather_requirements`/`generate_plan` involvement at all, so nothing about the
   requirements/planning stage runs.
4. LLM/parsing failures caught and returned as 502 with a clear message, matching `/agent/gather`'s pattern.

**Acceptance Criteria**
- Missing `code` and `files` (or an empty `files` list) → 400.
- Raw code, multi-file input, and a Git diff all produce a valid `CodeReviewReport` via this endpoint,
  reusing the same `diff_parser`/`review_code` logic as the main flow.
- `gather_requirements`'s and `generate_plan`'s LLM builders are never called for this endpoint (verified,
  not assumed).
- A review LLM failure returns 502, not a 500 or a crash.
- All prior tests still pass; this endpoint has no effect on `/agent/gather` or session storage.

**Testing & Verification**
- `test_review_endpoint.py` (7 tests): missing input, empty `files` list, raw code, multi-file boundaries,
  Git diff parsing, LLM-failure 502, and an explicit check that `_build_llm`/`_build_planning_llm` are never
  called when hitting this route.
- **Manual end-to-end run** (real `TestClient`, only the review LLM mocked): four real requests - missing
  input (400), raw code (200), two-file input (200, correct `=== FILE: ... ===` boundaries), and a real Git
  diff (200, correctly parsed to `=== FILE: db.py ===` with the actual hunk) - with the log output confirmed
  to show only `agent/review`/`review_code` lines, no `gather_requirements`/`generate_plan` activity.
- Full suite re-run: **48/48 passing** (41 prior + 7 new).

**Build Log (Issue, Fix, Decision)**
- **Issue:** none - implementation matched the plan on the first pass; the only open question was whether
  to route standalone review through a tiny second LangGraph graph or call the `review_code` function
  directly.
  **Decision:** call `review_code` directly. It's the same function used by the main graph (so "reuse the
  existing review agent" is literal, not just conceptual), and a second graph would add a moving part with
  no behavioral benefit for a single-node path - avoids overengineering per project rules.

**Deliverables**
- Updated `app/schemas.py`, `app/main.py`, `README.md`
- `tests/test_review_endpoint.py`
- Updated `project_summary.md`

**Objective**
Package the service as a Docker image and add CI that runs the test suite and validates the image build on

**Files to Create/Modify**

**Implementation Tasks**

2. `.dockerignore`: exclude `tests/`, `data/`, caches, `.env`, `.git`, `.github`.
3. `.github/workflows/ci.yml`: `test` job (checkout, setup-python 3.12, install deps, `pytest tests/ -v`);

**Acceptance Criteria**

- First start with an empty `data/` volume triggers ingestion automatically; a subsequent start with an
  already-built index skips re-ingesting.
- CI workflow YAML is valid and the test job runs the exact same `pytest tests/ -v` used locally.
- No existing test, schema, endpoint, or workflow behavior changes.

**Testing & Verification**
- **Sandbox limitation, disclosed directly:** this environment has no Docker daemon, so `docker build`
  itself could not be run or verified here. To compensate, every piece of logic the Dockerfile depends on
  was verified directly:
  - The `CMD`'s conditional ingest logic (`test -f .../index.faiss || python -m app.ingest`) was run
    standalone outside Docker - correctly detected the missing index and attempted ingestion (which then
    hit the same known sandbox-only HF network block from FL-06, not a logic error).
  - The exact `uvicorn app.main:app --host ... --port ...` command from `CMD` was run directly and
    confirmed serving real `/health` (200) and `/agent/review` (400 on empty body) responses.
  - `.github/workflows/ci.yml` was parsed with `yaml.safe_load` to confirm valid syntax.
- Full test suite re-run after adding these files (no app code touched): **48/48 passing**, unchanged.

**Build Log (Issue, Fix, Decision)**
- **Issue:** `yaml.safe_load` parsed the workflow's top-level `on:` key as the Python boolean `True`, not
  the string `"on"` - PyYAML follows YAML 1.1, where bare `on`/`off`/`yes`/`no` are booleans. GitHub's own
  workflow parser handles this correctly regardless, but it's a well-known footgun for any other YAML
  tooling touching the file.
  **Fix:** quoted the key as `"on":`. Re-parsed and confirmed `"on"` now appears as a real string key.
  **Decision:** documented this explicitly rather than leaving it as a silent correct-by-luck file, since a
  future edit removing the quotes would reintroduce it invisibly.
- **Issue:** first three attempts to run `uvicorn` in the background (to curl `/health`) returned connection
  refused with no log output at all, even after several seconds.
  **Fix:** ran the same command in the foreground instead, which showed the import chain alone takes ~5s
  (likely `langchain-google-genai`'s gRPC/protobuf setup) before uvicorn's startup banner even prints;
  re-ran the background version with a longer wait (15s) and it worked correctly.
  **Decision:** noted the ~5s cold-import cost as a real characteristic of this dependency stack, not a bug
  - worth knowing for container health-check `start_period` tuning later, but out of scope to fix now.
